What this page shows

A target's sdk.yml can declare extends: <base-target> to build on top of another target instead of duplicating its whole manifest. The diff against the base lives in a sibling overlay.yml. This page walks through a real 3-level chain from the cim-manifests repo: example → overlay-example → overlay-example-chain.

Fixed rules: a target's extends: only ever accepts a single base (chain single-parent levels to combine more than one ancestor — there is no extends: a,b list form). overlay.yml only ever holds remove:/modify: — there is no add:; anything new goes directly into that level's own sdk.yml lists. Removing/modifying an entry that doesn't exist in the inherited content is a hard error, not a silent no-op. Merge order per section is always remove → combine (base-after-removal + own new entries) → modify.

--include-group / --exclude-group

Filtering runs on the fully merged git list of overlay-example-chain (all three levels combined) — group membership is cross-level, it doesn't matter which level originally added a repository. A repo with no group: set implicitly belongs to the "default" group.

Note: group: isn't used in the real example manifests today. The group tags below (core / drivers / tests) were added purely to demonstrate the filter — look for the * marker.

FAQ

Can extends: target more than one base at once?

No. extends: only ever accepts a single base target (shorthand string or the structured {target, version, source} form). To combine content from more than one target, chain single-parent levels: A extends B, B extends C, etc.

What is overlay.yml allowed to do?

Only remove: and modify: against content inherited from the extends chain. There is no add: — new entries always go directly into that level's own sdk.yml lists, exactly as they would in a target with no extends: at all.

What happens if overlay.yml removes/modifies something that doesn't exist?

It's a hard error. Every remove:/modify: entry must reference a name (or dest: for copy_files) that already exists in the combined result — there's no silent no-op.

How does extends: name@version get resolved?

The shorthand form searches the same source list as the current target: config.toml's default_source then every alternate_sources entry, in order, first match wins. Use the structured {target, version, source} form to restrict resolution to one explicit source instead.

Can I use a full URL as the extends: value?

No — target: must stay a bare target name; cim always appends targets/<target>/sdk.yml onto whatever source resolves to. Put the URL in the structured form's source: field instead.

Does --include-group only look at the target named on the command line?

No — filtering runs on the fully merged git list (after the whole extends chain + overlay.yml is resolved), so it spans every level, not just the primary target's own sdk.yml.
